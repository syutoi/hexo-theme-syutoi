逐次指标、设置、环境、诊断摘要、请求大小及原始报告 SHA-256 见 [d8-performance.json](d8-performance.json)。完整 Lighthouse JSON 在本次机器的 `/tmp/syutoi-d8/`，不提交内嵌截图等大体积原始数据；运行下方脚本可重新生成。

## 核心资源预算

按 gzip level 9、1 KB = 1000 bytes 统计，包括生成文件中的注释。这里是离线压缩体积，并非本次 HTTP 的传输体积。

| 资源 | 原始字节 | gzip 字节 | PRD 上限 | 结果 |
| --- | ---: | ---: | --- | --- |
| `source/js/syutoi.min.js` | 3498 | 1334（1.334 KB） | <50 KB，争取 <30 KB | 两者均通过 |
| `source/css/syutoi.min.css` | 21312 | 5211（5.211 KB） | <40 KB | 通过 |

`pnpm check:budget` 输出大小与 SHA-256，超出严格上限时失败；已纳入 `pnpm test`。此预算只包含两份核心包，图片、HTML、feed、可选服务不在分母内，不应与页面总下载量混淆。

## 测试方法

- 使用 Node 20.19.2、独立安装的 Lighthouse 12.8.2、本机 Headless Chrome 151.0.7922.108。固定 Lighthouse 版本以兼容项目当前 Node；工具不加入主题依赖或锁文件。
- 将已生成的 `example/public` 通过 Python 静态 HTTP 服务暴露到 `127.0.0.1:4173`。无 gzip/Brotli、无生产缓存策略、无 CDN/TLS/真实服务器延迟；默认 dev 预览不作为本次测量源。
- 首页 `/` 与长文 `/syutoi-long-read/`，mobile 和 desktop 各 3 次，按顺序运行，各次使用新的 Chrome 配置目录。没有主动屏蔽资源或隐藏图片，也没有为测试改变主题。
- Lighthouse `throttlingMethod=simulate`，采用对应默认 mobile/desktop preset。模拟节流根据本地加载观察值建模，并非真实手机或公网测量；设置细节完整保存在 JSON。
- 只运行 performance 分类，不将这些分数当作 SEO、无障碍或最佳实践的验收结果。各指标独立取三次中位数，并保留最小/最大值；不是挑选最高分的一次。

本机 Linux 7.0.0-31-generic，Intel i7-1165G7（8 逻辑 CPU），约 15.36 GiB 内存。运行期间未并行启动构建或测试，但不是隔离的性能实验室。

## 实测结果

时间指标以秒或毫秒标明；括号为三次最小–最大值。CLS 无单位。

| 页面 / 模式 | Performance | LCP 秒 | CLS | TBT 毫秒 |
| --- | ---: | ---: | ---: | ---: |
| 首页 / mobile | 75（75–75） | 8.856（8.783–8.859） | 0.04850（0.04850–0.04850） | 0（0–0） |
| 首页 / desktop | 94（94–97） | 1.588（1.212–1.593） | 0.00039（0.00039–0.00039） | 0（0–12） |
| 长文 / mobile | 84（84–84） | 4.354（4.354–4.357） | 0.04850（0.04850–0.04850） | 0（0–0） |
| 长文 / desktop | 99（99–99） | 0.870（0.865–0.890） | 0.00000（0.00000–0.00039） | 0（0–0） |

- PRD LCP <2.5 秒：两类桌面页通过；两类移动页未通过。
- PRD CLS <0.1：12 次均通过。FCP、Speed Index 及未四舍五入数据保存在 JSON。
- 12 次没有 Lighthouse 运行警告，采集到的网络请求均为本地资源且 HTTP 200。这仅适用于这两个页面及本次导航，不能覆盖历史友链等其他页面的外链。
- PRD INP <200 ms：**未测得，不能判定通过**。本次为无交互的 navigation 测试。TBT 中位数为 0 ms 只能作为加载阶段主线程阻塞的参考，不能替代整次访问的 INP，也不能代表真实用户数据。

Lighthouse 的 [模拟节流说明](https://github.com/GoogleChrome/lighthouse/blob/main/docs/throttling.md) 解释了模型与实测网络的区别；Chrome 的 [INP 工具说明](https://developer.chrome.com/blog/inp-tools-2022) 说明实验室测量需要实际或脚本交互。后续需增加真实交互测量，并在部署后观察现场数据。

## 瓶颈与后续工作

首页首轮移动报告将 `.hero-image` 标为 LCP 元素。请求包含约 619 KB 的页头 JPG、742 KB 和 220 KB 的卡片 JPG；`uses-responsive-images` 估计可减少约 1.44 MB 图片下载，`image-delivery-insight` 也建议现代格式及尺寸优化。这是审计估算及优化线索，不能直接当作优化后实测收益；模型中的阶段归因也不等同于真实网络时间分解。

下一批 D8a 优先为示例图片提供合适尺寸与编码，在保留图片内容、波浪、卡片和整体布局的前提下降低传输量；如需主题 srcset/sizes 支持，应保持已有单 URL 配置兼容。随后按同一条件重复测量，并补查深浅模式及手机截图，防止以简化界面换取分数。

当前静态服务也被指出缺少文本压缩和长期缓存。生产部署文档应说明如何配置，但本批没有把离线 gzip 大小伪装为 HTTP 传输大小，也没有假设开启压缩就能解决全部 LCP 问题。D9/最终 PRD 验收仍需保留移动 LCP 和 INP 的未完成状态。

## 重复运行

在项目根目录使用项目要求的 Node（本次 20.19.2）：

```bash
pnpm build
pnpm check:budget
python3 -m http.server 4173 --bind 127.0.0.1 --directory example/public
```

另开终端，安装独立测量工具并运行：

```bash
npm install --prefix /tmp/syutoi-lighthouse-d8 --no-audit --no-fund lighthouse@12.8.2
export SYUTOI_LIGHTHOUSE_CLI=/tmp/syutoi-lighthouse-d8/node_modules/lighthouse/cli/index.js
export SYUTOI_CHROME=/usr/bin/google-chrome
export SYUTOI_PREVIEW_URL=http://127.0.0.1:4173
export SYUTOI_PERFORMANCE_OUTPUT=/tmp/syutoi-d8
node toolbox/check-performance.mjs
```

需预先安装 Chrome；脚本不下载浏览器。输出目录保存 12 份 Lighthouse JSON 与 `summary.json`。脚本遇到运行错误或缺失指标时失败，保留已完成组的摘要；只有带 `finished` 的汇总才代表全部完成。指标超出 PRD 目标仍会正常生成报告，本脚本用于记录基线，并未设置易受机器波动影响的 CI 分数门槛。提交新的测量记录前应审阅结果，不盲目覆盖历史基线。
