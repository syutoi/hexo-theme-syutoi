# G4：当前性能预算、Lighthouse 与交互测量

日期：2026-09-22。基线提交 f1e4515；优化轮使用同一提交加本批未提交的 Logo 副本与配置修改。**预算通过，但移动端首页 LCP 仍未达到 <2.5s；不能认定全部性能目标已达成。** 下一项 G4a 继续定位此瓶颈。

## 环境与方法

- Node 20.19.2、Lighthouse 12.8.2、Chrome 151.0.7922.108；完整 CPU、内存、系统信息与每次配置记录在 JSON。
- `pnpm build` 后用 Python 静态服务提供 example/public，地址 127.0.0.1:4173。无 HTTP gzip/Brotli、生产缓存、TLS/CDN 或公网延迟。
- 两轮都对首页和长文进行 mobile/desktop 各 3 次 Lighthouse navigation，每次新 Chrome profile。默认模拟节流：mobile 为 412×823、DPR 1.75、RTT 150ms、1638.4Kbps、4× CPU；desktop 为 1350×940、DPR 1、RTT 40ms、10240Kbps、1× CPU。
- 顺序测量，不与构建、测试、INP 或其他浏览器验收并行；普通开发预览保留运行，本机并非隔离实验室。没有屏蔽图片或第三方请求，也没有更换为简化页面。
- 指标各自取 3 次中位数，同时保留范围与全部原始报告哈希。不挑最高分、不混合两轮样本；环境差异可能影响与较早 D8a 的比较。

## Logo 优化

首轮发现导航显示 29×29 CSS px 的 Logo 下载了 1254×1254、346076 bytes 的 PNG。保留原图，生成 96×96 的 `source/images/logo.webp`（2558 bytes，减少约 99.26%），将默认配置和示例配置指向副本。没有改导航尺寸、图片内容、其他封面或布局；用户显式使用旧 PNG 路径仍可正常访问。

使用 cwebp 1.3.2，缩放后采用 lossless WebP 编码；命令见 [图片维护](../examples.md#导航-logo-的维护)。缩放并不是原始像素无损。没有新增构建依赖或浏览器脚本，核心 JS/CSS 字节不变。
